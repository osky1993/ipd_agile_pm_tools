# 演进落地计划：真实使用驱动的下一阶段

> 制定日期：2026-08-15。依据《IPD敏捷数字化工具箱-分阶段落地规划》§17「后续建设方向由真实瓶颈决定」。
> 本计划覆盖三块：**迭代 A（上车准备）→ 迭代 B（dogfooding 六周）→ 迭代 C（摩擦深化）**，技术债穿插其中。
> 阶段 6（组合管理）与被裁剪的阶段 5 条目（权限/SSO/多人并发）在本计划内明确不做。

工作量标记：S ≤ 半天；M = 1～2 天；L = 3～5 天。

---

## 0. 总节奏

| 迭代 | 时间窗 | 主题 | 出口判据 |
|---|---|---|---|
| A 上车准备 | 约 1 周（2026-08-18 ~ 08-22） | 保护网 + 备份例行化 + 真实项目建档 + 摩擦记录机制 | 真实项目在库、e2e 三条动线绿、每日备份自动跑 |
| B dogfooding | 6 周（2026-08-25 ~ 10-09） | 只用它、只修摩擦、不加新功能 | 见 §3.3 成功判据 |
| C 摩擦深化 | 2~3 周（10 月中起） | 主题由摩擦日志决定（三候选草案见 §4） | 对应候选各自的验收标准 |

核心纪律：**迭代 B 期间冻结新功能**。任何"想加的能力"一律先记为摩擦/候选，进入 §4 的决策漏斗，不当场实现。

## 1. 迭代 A：上车准备（1 周）

目标：让真实项目搬进来之前，把"改动有保护、数据有兜底、记录有机制"三件事备好。

### A1. e2e 薄保护网（L，本迭代最大项）✅ 已完成

dogfooding 期每周都会修摩擦，19 个页面靠手工走查护不住，先建三条最关键动线的 UI 自动化：

- 技术选型：Playwright，装在 `frontend/`（复用已有 npm 工程）。用例在 `frontend/e2e/`。
- 三条动线（**实际落地为 4 条用例，约 1 分钟跑完**）：
  1. 登录 → 「我的一天」正常聚合渲染（默认首页可用性）+ 今日焦点置顶。**反向断言四条空态文案不出现**——防「聚合接口挂了但页面静默空白」这类最典型的回归；
  2. 建需求 → 拉入迭代 → 经 **WorkItemDrawer 抽屉**走完一次状态流转 + 守卫拦截断言（⚠️ 已知坑：HTML5 原生拖拽合成鼠标事件触发不了，看板拖拽不做 e2e，一律走抽屉流转替代）。实测发现**守卫有两处**、走的是两条独立代码路径：`IterationService.checkAssignable`（拉入迭代）与 `guards/ReadyGuard`（流转 Ready），两处都断言；
  3. DCP 动线：铺条件模板 → 上传证据 → 发起评审 → 决策落库 + 基线自动固化断言。走「先判**通过**被红线拦，再改判**有条件通过**」——红线校验只作用于 PASS，而 CONDITIONAL 同样固化基线，一次拿到守卫/决策/基线三个断言，且不依赖把 6 条条件全刷成 MET（还要连带担心跨职能准备度红线）。
- 环境编排：新增 `deploy/e2e_ui.sh`。⚠️ 原计划写的「可参考 `e2e_demo.sh` 的环境准备段」不成立——该脚本假定系统已在运行，**没有**任何 docker/jar/健康检查/清理逻辑，这四段是全新编写的。
- **数据隔离（最重要的一条）**：dogfooding 期主库装的是真实项目，e2e 每次都写数据。改为起一套完全独立的环境——独立库 `ipd_toolbox_e2e` + 后端 18080 + 前端 15173 + 临时证据目录，跑前 DROP 重建让 Flyway 从零迁移（完全确定性，无需幂等技巧，顺带每次验一遍迁移在干净库上装得上）。原计划设想的「时间戳项目码不清库」被否决：决策只增不改、基线无删除入口，跑几十次就会把 `/trace`、`/baseline`、`/bigscreen` 这些跨项目视图淹掉。
- 三重保险防误删主库：库名必须以 `_e2e` 结尾、只 DROP 单库不碰命名卷、所有 DB 操作走 `docker exec` 容器名不经宿主机端口（顺带挡掉连错本机 23306 那个无关容器的可能）。兜底 kill 按 `-Dipd.e2e=1` 专属 JVM 标记匹配，**绝不**按 jar 名杀——那会误杀日常实例。
- 运行方式：`./deploy/e2e_ui.sh`（或 `npm run e2e --prefix frontend`）手动触发即可，单人工具不建 CI，也**不建议**装 git pre-push hook（每次 push 阻塞 1 分钟，与减少摩擦的目标相反）。改成纪律：**每周五过摩擦列表前先跑一次**，绿了再动手改下周的 Top 3，与 §2.1 已有的周五节律合流。
- 原则：**只护动线，不护像素**。断言业务结果（状态、守卫报错文案、决策记录存在），全程不使用 `toHaveScreenshot`。
- 定位策略：前端零 `data-testid`，本轮**不补**。选择器集中在 `frontend/e2e/support/fixtures.ts` 一处，改文案红了只改这一个文件。区分在于——驱动型定位用 CSS/结构，而守卫报错全文、状态中文名、空态文案一律硬断文案：**那些文案本身就是被保护的契约，改了就该有人确认**。
- ⚠️ 踩坑记档：`npm run build` 曾往工程根吐 `vite.config.js`，而 vite 解析配置时 **.js 优先于 .ts**，残留文件会静默顶掉 `vite.config.ts`（表现为前端起得来但所有接口 ECONNREFUSED）。已通过给 `tsconfig.node.json` 设 `outDir` 根治，脚本内另留了同名文件自动清理。

### A2. 备份例行化（S）

`deploy/backup.sh` / `restore.sh` 已有且实测过，缺的是"无人值守"：

- launchd plist（放 `deploy/` 下，`launchctl load` 启用）：每日凌晨跑 `backup.sh`；备份目录已在 .gitignore。
- 保留策略：近 14 天全量 + 每周留 1 份，脚本内滚动清理。
- **每月恢复演练一次**：restore 到临时库名（不覆盖主库），核对工作项计数与视图存在性后丢弃。演练日期记入摩擦日志机制（见 A4）。

### A3. 真实项目建档与数据迁移（M）

把一个真实在管的项目完整搬入，路径全部走已有能力，不为迁移写新代码：

1. 建项目、产品版本、阶段/DCP（DCP 条件用模板库一键铺，再删改不适用条目）；
2. 需求树用 Excel 层级导入（模板 `/work-items/import-template.xlsx`，序号 1/1.1/1.1.1 建树）；
3. 存量测试用例用 `/tests/import-template.xlsx` 导入（需求编号自动建 verifies）；
4. 在管风险/变更走 Excel 导入（已有 RiskChangeExcelService 通道）；
5. 历史决策若要补录：注意决策只增不改，按时间顺序录入让修订链自然成立；
6. 迁移完成后跑一次备份 + 时光机抽查（任选一天回放核对状态合理性）。

### A4. 摩擦记录机制（S）✅ 已完成

**用工具管理工具自己**——把「IPD 工具箱」自身注册为一个项目：

- 项目编码 **`TOOLBOX`**，建档脚本 `deploy/seed_toolbox_project.sh`（幂等，可重复执行）。三个候选（C1/C2/C3）已录入，停在 OPEN 不流转；另有一条真实摩擦作为四要素模板的可照抄样板。
- 每条摩擦记为该项目下的 improvement（复用 OPEN→DOING→DONE→VERIFIED 闭环），**「措施」字段**里固定四要素：**场景 / 频次 / 单次耗时或绕过方式 / 期望**（`improvement` 无独立描述字段，`measure` 是唯一的长文本承载位，TEXT 类型）。
- 大颗粒候选（明显是 L 级的能力诉求）打上约定前缀「**候选：**」，只记录不启动，留给迭代 C 决策。
- **数值口径统一为「该摩擦每周消耗的分钟数」**：`baselineValue`=现状、`targetValue`=目标、`resultValue`=修复后实测，语义细节写 `conclusion`。这条是被逼出来的约定——`ImprovementService.transition` 进 VERIFIED 时**强制校验 `resultValue` 非空**（DECIMAL(10,2)），不绑指标就不会自动取值，所以本计划原先举例的「录入耗时 30s→8s」这种字符串存不进去。好在这个口径正好就是 §2.1「按频次×耗时排序」的排序依据。
- 检索：improvement **无标签字段**，`list()` 只支持 projectId + status 两个过滤条件，也不进全局搜索/看板/MCP。为让「候选：」前缀真的可筛，已在效能页改进项 Tab 加了标题关键词框（纯前端 1 个 ref + 一个过滤条件）。
- 这样迭代 B 结束时，摩擦日志本身就是一份可检索、可统计、走过闭环的数据集，也是对 improvement 功能的真实验证。

### A5. 汉化清扫（S，顺手）

按既有清单清掉剩余英文文案：后端拼接文案里的英文状态、角色标签、审计 action 列。属于 dogfooding 前的观感整备，半天内收口，不扩大范围。

## 2. 迭代 B：dogfooding 六周

### 2.1 使用节律

- **每日**：以「我的一天」开工；工作项状态当天流转当天记；摩擦当场记（见 A4），不攒。
- **每周五（约 1 小时）**：过一遍摩擦列表 → 按频次×耗时排序 → 挑 Top 3 个 S/M 级排入下周修复；周报页顺手看一眼本周 diff 是否符合体感（这本身也在验证周报功能）。
- **每两周**：若真实项目有迭代节奏，用迭代复盘页做一次复盘并沉淀 lesson——组织资产功能的真实验证点。

### 2.2 修复批次规则

- 只修摩擦：S/M 级当周修，修完在 improvement 上走到 VERIFIED（填实际值，如"录入耗时 30s→8s"）；
- L 级一律进候选池，不在迭代 B 动手；
- 每周修复日 ≤ 1 天，其余时间是"用"不是"改"——比例失衡本身就是一个要记录的信号；
- 每次修复前跑 `./deploy/e2e_ui.sh` + `mvn test`（当前 **118** 单测），绿了再动手，修完再跑。

### 2.3 成功判据（第 6 周末核验）

| 判据 | 目标 |
|---|---|
| 使用频度 | 每周实际使用 ≥ 4 天，「我的一天」为每日首开页 |
| 替代性 | 项目状态、风险、待办不再另记 Excel/备忘录（出现"退回"即记录退回场景） |
| 数据鲜度 | 工作项状态与实际偏差 ≤ 1 天 |
| 摩擦趋势 | 新增摩擦速率后三周较前三周明显下降 |
| 闭环验证 | ≥ 10 条 improvement 走到 VERIFIED |

### 2.4 中止与调整条件

- 若第 3 周仍在成规模退回 Excel：暂停修小摩擦，把"退回的那个场景"升级为唯一主题，直接进入迭代 C 提前处理；
- 若真实项目本身节奏中断（外部原因）：顺延时间窗，不缩短六周的有效使用时长。

## 3. 迭代 C：摩擦深化（主题由数据决定）

### 3.1 决策规则

第 6 周末把摩擦日志按类别计数（提醒缺失 / 录入成本 / 性能等待 / 其它），**取最大类别为迭代 C 主题**；若无明显头部类别，按下述预判优先级：提醒 > 录入 > 性能。三候选草案如下，仅其一（至多其二）启动。

### 3.2 候选 C1：主动提醒（预判最可能）

单人工具没有"别人催你"，分三级阶梯，从零后端改动开始验证粘性：

1. **晨报脚本（S）**：`deploy/daily_brief.sh` 调既有 API（我的一天聚合 + 预警列表），生成 Markdown 晨报并经 `osascript` 发 macOS 通知，launchd 每早触发。零后端改动。
2. **若晨报被证明每天看（M）**：通知分级——超期/DCP 临近（14 天窗口规则已有）单独弹，其余归入晨报摘要。
3. **只有前两级都嫌不够时（L）**：后端进程内 scheduler + 通知记录表。默认不做，避免为单人场景建通知中心。

### 3.3 候选 C2：录入成本

QuickCreateDialog + 快捷键 + 批量 + Excel 已在，若仍嫌重，方向是"先接住、后整理"：

1. **收件箱模式（M）**：一行速记落为 Backlog 特定标记项，每周五整理时再补类型/归属/估算；
2. **AI 拆分剧本（S~M）**：不写新代码，在 `docs/06-AI操作手册.md` 增补剧本——把一段口语描述经 MCP `create_work_items`（默认 dry_run）拆成带层级的工作项，预检后确认落库。基建（batch-create + dryRun）已备。

### 3.4 候选 C3：性能实测与优化

不预先优化，先测再说：

1. **造数放大（S）**：仿 seed 脚本造 5000 工作项 / 5 万条状态日志的压测项目；
2. **基准（S）**：实测时光机 replay（含 A/B 对比双回放）、CFD、perf trends 三类接口耗时，阈值定为交互可接受的 1.5s；
3. **超阈值才优化（M~L）**：优先顺序——索引核查 → 回放按项目分区 → 月度快照 + 增量回放（改动最大，最后考虑）。

## 4. 技术债处理策略

| 债项 | 策略 | 触发/时机 |
|---|---|---|
| `ext_fields` JSON 语义超载（wsjf/probability/impact/strategy…） | 观察，不预先重构。**升格规则**：某 ext 键一旦成为列表高频过滤/排序条件，或需要跨项目 SQL 聚合，即升格为实体列（Flyway 迁移 + 存量回填 + 读写兼容一版） | 迭代 B/C 中按规则触发 |
| JWT + RBAC 多用户残留 | **冻结不投入**：不删（JWT 是 MCP 365 天 api-token 的鉴权基础），不扩展，不再围绕它做任何建设。在 README 定位段加一句声明即可 | 迭代 A 顺手声明 |
| 前端回归靠手工走查 | A1 的三条 e2e 动线即为答案（已建成）；后续**只在"某动线在迭代 B 被改坏过"时**才为其补 e2e，不追求覆盖率 | ✅ A1 已建成，后续按需 |
| 汉化剩余（后端拼接文案/审计 action 列） | A5 一次收口 | 迭代 A |
| 备份无人值守 + 恢复未例行演练 | A2 launchd + 每月演练 | 迭代 A 起长期 |
| 时光机/CFD 全量回放的体量风险 | 不动，转入 C3 用数据说话 | 迭代 C 视基准结果 |

## 5. 明确不做（本计划期内）

- 阶段 6 组合管理（启动条件"两个真实项目完成使用验证"不满足）；
- 数据范围权限、SSO、多人并发（定位裁剪，规划文档已确认）；
- 通知中心式的大建设（C1 阶梯第 3 级默认不做）；
- 全量 e2e / 像素回归；
- 未经过摩擦日志漏斗的任何新功能。
